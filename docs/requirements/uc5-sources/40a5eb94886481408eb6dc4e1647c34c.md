## 1. Selected architecture

| Component | Test | Live |
| --- | --- | --- |
| Frontend | React/Vite/TypeScript on private S3 + CloudFront | Separate private S3 + CloudFront |
| Backend | EC2 <b>t4g.micro</b>, 2 vCPU/1 GiB ARM64, Amazon Linux 2023, Docker Compose, Caddy, Spring Boot/JDK 25 (upgrade to t4g.small/2 GiB if workload needs it) | Separate EC2 <b>t4g.small</b> initially; review t4g.medium (4 GiB) after representative Xero/vWork sync tests |
| EC2 region | AWS Sydney <code>ap-southeast-2</code> | AWS Sydney <code>ap-southeast-2</code> |
| Root storage | <b>10 GiB encrypted gp3 EBS</b> initially, monitor disk pressure | 20 GiB encrypted gp3 EBS initially, adjustable |
| Database/Auth | Separate Sydney Supabase Test project, synthetic data | Separate Sydney Supabase Pro project |
| External integrations | Xero demo/development app; vWork sandbox or restricted non-destructive test only | Authorised production Xero/vWork tenants and credentials |
| Source, CI/CD | One private GitHub repo; GitHub Actions; AWS OIDC | Same versioned build/image, manual approval-controlled promotion |
| Images | Amazon ECR private repository, ARM64 image | Same immutable image digest promoted from Test |
| Admin/deployment | AWS Systems Manager Session Manager and Run Command; no inbound SSH | Same, separate IAM permissions and approval |
| Secrets | Test-only SSM Parameter Store SecureString; Secrets Manager if rotation is required | Production-only secret paths, stricter access and rotation |
| TLS | Caddy + Let's Encrypt on EC2 API; default CloudFront HTTPS for frontend (ACM us-east-1 only if custom domain) | Caddy + Let's Encrypt on EC2 API; CloudFront/ACM on custom frontend domain |
| Recovery | Rebuild EC2 from documented template/bootstrap; disposable/synthetic DB seed | EBS snapshots + Supabase backups + tested restore; keep known-good container image |

<b>Design rules:</b> One backend modular monolith, no Kubernetes, ECS, ALB, NAT Gateway, bastion host, public SSH, or RDS at launch. Test and Live do not share hosts, databases, Auth projects, secrets, IAM deployment roles or external write-capable API tenants. Local React and Spring Boot may connect to Supabase Test; destructive CI tests require disposable PostgreSQL. JDK 25 LTS is mandatory in local development, CI and both runtime images. Confirm Java 25 and dependent native libraries work on ARM64.

## 2. High-level connectivity

```txt
                          GitHub (single repository)
                       GitHub Actions + AWS OIDC
                                  |
                     Build/test; push ARM64 image
                                  v
                         Amazon ECR (private)
                            /           \
                     TEST release      LIVE promotion
                     approved merge    manual authorisation
                           |                 |
                 SSM Run Command      SSM Run Command
                           |                 |
                  EC2 Test (1 GiB)    EC2 Live (2 GiB*)
                  AL2023 + Docker     AL2023 + Docker
                  Caddy + Java 25     Caddy + Java 25
                           |                 |
                  Supabase TEST       Supabase LIVE
                  DB + Auth           DB + Auth
                           ^                 ^
               private S3 Test        private S3 Live
                 + CloudFront           + CloudFront
                       ^                     ^
                 Browser/Test         Browser/Production

* If Test Java 25/SSM/Docker exceeds micro memory, upgrade Test to t4g.small (2 GiB). Review Live t4g.medium (4 GiB) after representative load testing.
```

Browser → CloudFront frontend assets; browser → corresponding Supabase Auth; browser → corresponding EC2 API over HTTPS; EC2 → corresponding Supabase PostgreSQL over TLS and Xero/vWork APIs over HTTPS. ECR and Systems Manager use authenticated AWS IAM access. No production data or OAuth refresh tokens may reach Test.

## 3. AWS account foundations

1. Protect AWS root with phishing-resistant MFA/passkey or security key, a unique password and secure recovery process. No root access keys. Use root only for root-only operations.
2. Set up IAM Identity Center for named administrator access with MFA and short-lived sessions; avoid permanent IAM-user access keys. Give separate admin, readonly, Test deploy and Live deploy permissions.
3. Restrict GitHub OIDC trust to the exact repository, expected branch/environment claims and audience. Use different Test and Live deployment roles and resource tags.
4. Production CI must not have autonomous authority to promote a release. Require explicit human release approval. Verify current GitHub-plan support for environment reviewers; otherwise use a separate restricted manual production workflow.
5. Set account billing contact and AWS Budgets alerts before provisioning, with a budget reflecting the new EC2 baseline.

References: [AWS root best practices](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html), [AWS account administrator best practices](https://docs.aws.amazon.com/signin/latest/userguide/best-practices-admin.html).

## 4. Network and access

<b>Initial low-cost network:</b> One VPC in Sydney with a public subnet for each internet-facing API EC2 instance. Use an Internet Gateway and a public IPv4 address / Elastic IP where stable API DNS requires it. <b>Do not create a NAT Gateway or load balancer merely to conceal the server.</b> Public subnet placement does not permit unrestricted access: security groups control inbound traffic.

| EC2 security-group direction | Protocol/port | Source/destination | Purpose |
| --- | --- | --- | --- |
| Inbound | TCP 443 | Internet | HTTPS API via Caddy |
| Inbound | TCP 80 | Internet only if needed for ACME HTTP-01 and redirect | Certificate issuance/redirect |
| Inbound | TCP 22 | <b>No rule</b> | No public SSH |
| Inbound | TCP 8080, 5432, 2375/2376 | <b>No rule</b> | Spring Boot, database and Docker are not internet-exposed |
| Outbound | TCP 443 | Approved AWS/Supabase/Xero/vWork endpoints, initially broad outbound with monitoring | SSM, ECR, API integrations and updates |
| Outbound | TCP 5432/6543 or Supabase supported DB port | Supabase database endpoints only | PostgreSQL TLS connections; validate actual connection method/port |
| Outbound | DNS/NTP as required | VPC DNS/time services | Resolution/time |

Security groups are stateful. Reduce outbound scope where practical, but do not break managed package updates, SSM, ECR or third-party APIs. Protect Caddy's upstream: bind Spring Boot Docker port to loopback/container network only, never 0.0.0.0 on host.

<b>SSM:</b> Prefer Session Manager for admin and Run Command for CI/CD. Install/verify SSM Agent and attach <code>AmazonSSMManagedInstanceCore</code> to the EC2 instance role. The instance makes outbound HTTPS connections to Systems Manager endpoints; no port 22 is needed. Record/retain shell session logs where supported, tightly scope <code>ssm:StartSession</code> and <code>ssm:SendCommand</code>, and use named IAM identities. Session Manager is an administration transport, not a substitute for application authentication. Run Command permissions are powerful and must be tightly restricted.

<b>Private subnets:</b> Reserve them for any future internal AWS databases/worker services. The current DB is <i>external managed Supabase</i>, not an EC2/RDS database inside the VPC. Placing the EC2 API in a private subnet would require paid NAT or multiple VPC endpoints plus other outbound connectivity for Supabase/Xero/vWork. Reconsider a private EC2 + ALB arrangement when compliance, budget or scale justifies the added cost.

References: [SSM Agent network requirements](https://docs.aws.amazon.com/systems-manager/latest/userguide/troubleshooting-ssm-agent.html), [Public IPv4 charges](https://aws.amazon.com/vpc/pricing/).

## 5. Instance launch and host hardening

- EC2 AMI: current <b>Amazon Linux 2023 ARM64</b> vendor-maintained minimal/base AMI, pin the selected AMI ID in IaC after testing and update routinely. Confirm SSM Agent is installed/active.
- Instance: <b>Test t4g.micro</b> (2 vCPU, 1 GiB ARM64) initially, upgrade to <b>t4g.small</b> (2 GiB) if Java 25, Docker, Caddy and SSM exhaust memory; <b>Live t4g.small</b> (2 GiB), review <b>t4g.medium</b> (4 GiB) after representative sync/load tests. T4g burstable CPU credits can incur additional charges in Unlimited mode; monitor credit balance/surplus.
- Storage: <b>Test 10 GiB encrypted gp3</b> root volume; <b>Live 20 GiB encrypted gp3</b> root volume. Explicitly monitor Test free space (AL2023, Docker layers, logs, Caddy data); resize if necessary. Use AWS-managed KMS encryption initially, review DeleteOnTermination, and enable regional EBS encryption by default.
- Metadata: <b>IMDSv2 required</b> (HttpTokens=required; restrictive hop limit). Attach an instance IAM role rather than putting access keys on disk. Restrict instance role to SSM, read access to its own environment secret paths and pulling approved ECR images.
- SSH: do <b>not</b> create/publicly expose SSH by default. If break-glass SSH is ever enabled, restrict TCP 22 to known IP/VPN, use an individual key pair, disable password authentication and root login, document expiry and remove the rule after use.
- Host: install only Docker/Compose, Caddy (can be run as a separate container), SSM/CloudWatch agents and essential packages. Run the Java application as non-root, Docker root access limited to trusted deploy/admin identities. Apply automatic security updates with controlled reboots and restart checks; patch OS, Docker, Java 25 image and application dependencies regularly.
- Docker Compose: one version-controlled service definition; env-specific settings supplied securely at deployment. Restrict privileges, apply restart policies and memory/CPU limits, retain disk space and rotate logs. Do not embed secrets in Docker images or git.

Reference: [SSM agent on AMIs](https://docs.aws.amazon.com/systems-manager/latest/userguide/ami-preinstalled-agent.html).

## 6. Data protection and application security

- Frontend: private S3 bucket per environment, Block Public Access and CloudFront Origin Access Control; CloudFront HTTPS using ACM certificate, correct SPA fallback and cache handling. No secrets in JavaScript builds.
- API: HTTPS via Caddy/Let's Encrypt; secure headers and environment-scoped CORS. Verify Supabase JWT issuer, signature, audience and expiry in Spring Security, then perform independent user-role and three-entity permission checks on every API request.
- Database: unique Supabase project per environment, restricted SQL credentials, TLS, small connection pool. Use a single version-controlled migration history (Supabase CLI as specified in the existing implementation plan; <b>do not also use independent Flyway history</b>). Apply migrations via controlled process, never destructive CI against shared Test.
- Secrets: store non-rotating small configuration/credentials as SSM Parameter Store Standard SecureString when suitable and access controls are sufficient; use AWS Secrets Manager for credentials requiring automatic rotation/finer lifecycle controls. Scope IAM/KMS permissions to each environment. Keep Xero OAuth refresh tokens encrypted in a server-side durable store with per-environment access controls; never in frontend, GitHub or logs.
- Integrations: use Xero development app/demo company for Test; production orgs and vWork integrations only in Live. Keep OAuth token refresh, rate-limit handling and audit state durable in the database.

References: [Parameter Store](https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-parameter-store.html), [SecureString vs Secrets Manager](https://docs.aws.amazon.com/systems-manager/latest/userguide/what-is-a-parameter.html).

## 7. CI/CD and reproducibility

1. GitHub Actions runs Java 25 and React tests, dependency/secret checks, migration validation, and builds a pinned <b>linux/arm64</b> Docker image.
2. Assume an environment-specific AWS deployment role via GitHub OIDC; publish immutable image digest to private Amazon ECR. No AWS long-lived keys in GitHub.
3. Approved merge deploys to Test: controlled Test migration, SSM Run Command targeted only at EC2 Test; instance role pulls specific ECR image, updates Docker Compose, health-checks Spring Boot and checks HTTPS.
4. After verified Test, a <b>separate manually authorised</b> workflow promotes the <i>same image digest</i> and approved database migration to Live. Apply backward-compatible schema changes and preserve previous image for rollback.
5. Use a concise CloudFormation template or repeatable bootstrap script for EC2, security group, instance profile, encrypted EBS, S3/CloudFront/IAM and monitoring. Infrastructure modifications should be reviewed and separate from routine app deployments. Never run destructive prod actions automatically.

## 8. Observability, backups, cost and reliability

- <b>CloudTrail:</b> 90-day management Event history is available without creating a paid trail. For durable account/security audit history, configure a multi-region management-events trail into protected S3 with retention (S3/log charges apply).
- <b>CloudWatch:</b> basic EC2 metrics and alarms for status check, high CPU, CPU credits, EBS/storage capacity via CloudWatch Agent, memory, Docker restarts and application health; alert on API errors and failed Xero/vWork sync. Set log retention and redact passwords, JWTs, OAuth tokens and sensitive financial payloads.
- <b>GuardDuty:</b> enable foundational protection if budget permits; check paid usage after the 30-day trial. Explicitly review optional protection plans/monitoring additions before enabling; GuardDuty is usage billed, not a fixed-cost free service.
- <b>AWS Budgets:</b> set alerts near agreed AWS ceiling and forecast threshold. Budget alerts notify; they do not automatically cap spending. Monitor EBS, public IPv4, snapshots, CloudWatch, CloudFront, CloudTrail data events, GuardDuty and T4g surplus credits.
- <b>Backups:</b> scheduled production EBS snapshots via Data Lifecycle Manager or AWS Backup; retention policy and alarm on failures. Supabase Live backups have a separate documented restoration procedure. Test is primarily rebuilt from version-controlled migrations + synthetic seed. Rehearse EC2 rebuild, secrets reattachment, DNS/certificate, Docker deployment and Supabase restore before production.
- <b>Reliability:</b> a single EC2 host per environment is a <b>single-AZ failure domain</b>, not HA. Configure automatic process restart, EC2 instance recovery where supported, monitoring/alerts, tested rebuild, and a documented maintenance window. Define acceptable RTO/RPO with the client before launch.

## 10. New Zealand Privacy Act 2020 and offshore processing

Air Concepts is a NZ business; Sydney hosting is <b>offshore processing</b>. Document what customer, staff, invoice and token data flows through AWS, Supabase, Xero and vWork and their subprocessors, backups, logs, support access and telemetry. Confirm responsibilities and processor arrangements with the client, and apply the Privacy Act 2020's safeguards, purpose limitation, access controls, breach handling and retention requirements.

<b>IPP 12 requires care but does not mean every Australian-hosted cloud service automatically constitutes a restricted disclosure.</b> The NZ Privacy Commissioner distinguishes an overseas disclosure to another agency from a cloud/service provider storing or processing on behalf of the NZ agency (section 11). When a genuine overseas disclosure occurs, establish comparable safeguards, contractual protection, applicable law or another lawful basis; informed authorisation has particular requirements. Assess the actual arrangement rather than assuming Sydney region selection alone establishes compliance. Do not describe this technical design as legal certification. Obtain legal/privacy advice if data classification or contractual obligations require it.

Sources: [NZ Privacy Commissioner — IPP 12](https://www.privacy.org.nz/privacy-principles/12/), [Can I send information overseas?](https://www.privacy.org.nz/resources-and-learning/knowledge-base/view/219/).

## 11. Immediate implementation sequence

1. Account ownership/root MFA, IAM Identity Center, AWS budget and Test-only OIDC role.
2. Create Supabase Test/Auth and the isolated schema/seed process.
3. Provision <b>EC2 Test t4g.micro, 10 GiB encrypted gp3</b> in Sydney using one CloudFormation template for EC2, IAM/SSM, ECR, private S3/CloudFront and basic monitoring; AL2023 ARM64, IMDSv2 required, <b>no inbound 22</b>, verify Session Manager.
4. Install/pin Docker Compose and Caddy, configure HTTPS, non-root Java runtime, patching and logs; verify Supabase TLS connection.
5. Set up Test private S3/CloudFront; create ECR; implement GitHub Actions Test deployment via OIDC + SSM Run Command.
6. Validate smoke tests, Test memory/disk/CPU credits and image rollback/recovery; upgrade Test from t4g.micro (1 GiB) to t4g.small (2 GiB) when measured memory demands it. Review any further capacity change separately.
7. Only after Test validation and owner approval, provision separate Live resources with production backups, secrets, alerts, approved release gate and privacy documentation.

<b>Open decisions:</b> DNS/domain and AWS ownership; whether Test is always-on; final acceptable monthly AWS budget; Test t4g.micro (1 GiB) workload validation and possible 2 GiB upgrade; Xero/vWork test access; email SMTP; client privacy/backup requirements. Existing development/functional requirements and agent collaboration process remain otherwise unchanged.
