## Architecture baseline

| Area | Current plan |
| --- | --- |
| Local development | VS Code; React/Vite on [localhost](http://localhost) and JDK 25 LTS/Spring Boot on [localhost](http://localhost) are allowed |
| Backend architecture | Modular monolith, separate from React frontend; Maven Wrapper |
| Frontend | React, Vite, TypeScript; private S3 + CloudFront for deployed environments |
| Backend hosting | Separate AWS EC2 t4g.small (2 GiB ARM64) instances in Sydney for Test and Live; Amazon Linux 2023, encrypted gp3 EBS, Docker Compose + Caddy + JDK 25 Spring Boot; validate 2 GiB and upgrade to t4g.medium (4 GiB) as required |
| Database and Auth | Separate Supabase PostgreSQL/Auth projects for Test and Live; hosted Test reused for normal local development |
| Test data | Synthetic only; isolated ephemeral PostgreSQL for destructive/automated integration tests |
| Integrations | Test Xero demo organisation and development OAuth app; production Xero tenants only in Live |
| Source and delivery | Private GitHub, protected main, GitHub Actions OIDC → ECR ARM64 immutable images → Systems Manager Run Command for EC2 deployments; separate Test/Live IAM permissions |
| Infrastructure | Simple, reviewed EC2/S3/CloudFront infrastructure templates and auditable host bootstrap scripts; use one small <code>infra/cloudformation/test-ec2.yaml</code> template for Test EC2, security group, encrypted EBS and instance role, with short Docker/SSM UserData bootstrap before first instance launch; no NAT Gateway or ALB at launch |
| Change control | Agents propose requirements/changes and open PRs; CI verifies; Live deployment requires explicit approval |

<b>Environment safety:</b> Local and hosted Test must never use production Supabase or Xero credentials. Agents must not be given production credentials or autonomous Live deployment rights. Do not automatically run local migrations against the shared Test database. Keep schema migrations version-controlled and apply through controlled CI. Live must have independent infrastructure, data, Auth, secrets and deployment privileges.

## Milestone 1 — Development workspace and agent framework

1. Create private GitHub repository <code>air-concepts-dashboard</code>; configure issues, branch protection, PR policy, Actions, review requirements and local VS Code toolchain.
2. Define <code>AGENTS.md</code> for shared coding rules, <code>CLAUDE.md</code> for Claude, shared security/permission boundaries; custom agent skills are optional later.
3. Add task/issue templates and a requirement-refinement workflow: task → proposed technical spec → approval → failing tests → implementation → independent review → PR.
4. Import approved Notion requirements into version-controlled engineering references, preserving links/IDs. Record current decisions as architecture decision records, without silently changing client scope.
5. Generate JDK 25/Spring Boot backend and React/Vite frontend skeletons, with basic health checks and smoke tests.

<b>Exit criterion:</b> Both agents can read the same instructions and independently run a guided task; a private repository contains a compiling application skeleton and documented source links.

## Milestone 2 — Hosted Test data and local developer loop

1. Create Sydney Supabase Test project in a separate Test organisation (Free plan initially), with Auth, dedicated credentials and synthetic users.
2. Configure version-controlled Supabase SQL migrations and repeatable synthetic seed; designate a single schema migration owner (Supabase CLI, not a second Flyway migration history).
3. Configure local Spring Boot and React to use Supabase Test project only; implement configuration validation, backend JWT validation, role check skeleton and [localhost](http://localhost) CORS.
4. Create unit/component/API/integration test harnesses (JUnit/Mockito, Spring Boot Test, Vitest/React Testing Library, Playwright) and isolated PostgreSQL in CI.
5. Protect Test database from destructive tests or uncontrolled local migrations.

<b>Exit criterion:</b> Local frontend and backend run against hosted Test Auth and DB; CI tests can run without destroying shared Test state.

## Milestone 3 — CI and Test infrastructure

1. Add GitHub Actions PR checks: JDK 25 backend verify, frontend lint/test/build, dependency/secret scanning and infrastructure lint.
2. Secure AWS account: root MFA, IAM Identity Center admin access, AWS Budgets, CloudTrail; configure GitHub OIDC scoped to Test and environment-specific Parameter Store/Secrets Manager permissions.
3. Provision Sydney EC2 Test t4g.small (2 GiB ARM64) with Amazon Linux 2023, encrypted gp3 EBS, IMDSv2 required, least-privilege instance profile, Internet Gateway/public subnet and security group allowing HTTPS only (HTTP for certificate handling if needed); <b>no inbound SSH</b>. Enable Systems Manager Session Manager/Run Command over outbound HTTPS. Use one reviewed <code>infra/cloudformation/test-ec2.yaml</code> with minimal Docker/SSM UserData; do not launch the initial stack before its bootstrap is included.
4. Check the EC2 UserData installed Docker/SSM, then create version-controlled <code>deploy/compose.yaml</code> and <code>deploy/Caddyfile</code>. CI-002 delivers them to EC2 using SSM along with the ARM64 Java 25 image; enable HTTPS, non-root runtime, log rotation, resource limits and Test-only secret reads.
5. Create private Test S3/CloudFront/OAC and ECR; GitHub Actions tests/builds/pushes a pinned ARM64 image and deploys via OIDC + Systems Manager Run Command after controlled Test SQL migrations. Publish a matching React artifact.
6. Add basic CloudWatch metrics/log retention/alerts, GuardDuty cost review, EC2 recovery procedure and EBS snapshot policy; record release ID, smoke/E2E test results and rollback rehearsal.
7. Measure JDK 25 process/container RAM and burstable CPU during representative Xero/vWork sync; keep 2 GiB only if validated, otherwise scale Test to t4g.medium (4 GiB).

<b>Exit criterion:</b> Merging an approved change builds, tests and deploys a reproducible release into AWS Test; failures are visible and recoverable.

## Milestone 4 — Green Lane pilot (provisional)

Use <mention url="https://app.notion.com/p/4095eb948864813cb6b6e63dc598bdda" /> as the first end-to-end implementation. Refine each subtask to an approved technical specification before coding.

- Email six-digit OTP login, 10-minute expiry, allowed users, active/inactive status and server-side roles.
- Entity creation and Xero OAuth integration; server-side tenant mapping to the three organisations.
- Read-only invoice retrieval, pagination, entity-scoped filtering/search and invoice details.
- Dashboard-owned invoice assignments, role restrictions and persistence across Xero refresh.
- Acceptance testing with Xero demo company, cross-entity security tests and a client demonstration.

<b>Exit criterion:</b> Approved Use Case 5 acceptance criteria pass on Test; larger dashboard use cases remain independently prioritised.

## Milestone 5 — Live readiness (do not execute automatically)

After Test is proven and approved, provision separate EC2 Live t4g.small (2 GiB initially; 4 GiB t4g.medium if load requires), isolated IAM/SSM/ECR deployment permissions, private frontend, and Supabase Pro project. Use same immutable ARM64 image promoted through a manually approved GitHub workflow and Systems Manager Run Command. Implement production migrations, SMTP, EBS snapshots, Supabase backups/restore, CloudTrail/CloudWatch alerts, GuardDuty cost review, runbooks and NZ Privacy Act 2020/IPP 12 cross-border data-flow assessment before launch. Do not provision or deploy Live autonomously.

## Definition of Done (engineering tasks)

- Approved linked requirement(s) and documented acceptance criteria.
- TDD evidence: initial expected failure then passing implementation, where applicable.
- Automated unit/integration/API/component tests, including negative cases and security boundaries.
- CI passes and relevant dependency/security checks completed.
- DB and IaC changes reviewed; no production secrets/data exposed.
- Documentation and requirement traceability updated.
- PR reviewed; hosted Test acceptance/smoke verification when applicable.
- Rollback/operational impact recorded for deployment changes.

## Workflow and change management

1. Notion contains business source requirements and this evolving delivery plan; GitHub Issues hold implementation tasks once repository exists.
2. Record one agent-owned feature branch per task. Claude Code and Codex share a compact engineering contract; a second agent may review the PR.
3. Stop at the specification checkpoint if requirements, permission policy, external integration behaviour or business rules need approval.
4. CI must verify claims of test success; agents cannot self-approve releases.
5. Update tasks and this page after an architecture decision, validated technical spike or milestone. Preserve the task/decision history; add/re-scope work instead of rewriting completed evidence.
6. Do not assign firm dates, effort or client commitments until the prerequisites and full delivery scope are confirmed.
