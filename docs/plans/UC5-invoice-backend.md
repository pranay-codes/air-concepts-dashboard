# UC5 invoice backend execution contract

Goal: authenticated, entity-scoped, read-only invoice and supplier-bill retrieval, followed by sales assignments and secure attachments. Constraints: provider-side filters/pagination, no accounting writes or successful stale data, active database roles, server-selected tenant, no provider payloads or tokens in errors. Failures must remain explicit and recoverable.

Files: `invoices/InvoiceViews`, `InvoiceService`, `xero/XeroInvoiceClient`, `web/InvoiceController`, Xero transport configuration and matching tests. Subsequent assignment/attachment changes receive their own tests and migration where required.

Definition of Done for retrieval: list and detail HTTP routes enforce the role matrix before transport; query values are validated; provider pages include consistent full-result totals; wrong document type/ID, malformed responses, permission/rate/transport failures never produce success; nullable financial values are retained; dates use the Auckland business calendar for overdue. Mock transport and service/HTTP tests pass, OpenAPI/types agree. Demo pagination/search/sort semantics remain an explicitly separate runtime check.

Sequence: write failing provider and service tests, implement and verify retrieval, add HTTP contract tests, regenerate schema/types; then implement assignment persistence and bounded secure attachments. No hosted database or Live actions.

Provider evidence checked 7 November: official requests-and-responses documentation specifies lower-case `pagination` with `page`, `pageSize`, `pageCount`, `itemCount`. The invoices endpoint supports bounded paging and returns line items for paged records. Missing paging metadata is an error, never a guessed total. Official documentation: https://developer.xero.com/documentation/api/accounting/requests-and-responses/ and https://developer.xero.com/documentation/api/accounting/invoices . Full-result Contains/compound sort behaviour still needs the demo contract check recorded in the spike.

Assignment contract: `PUT /entities/{entityId}/invoices/{invoiceId}/assignment`, nullable `assigneeId` unassigns. Only ACCREC, verified by provider detail before any metadata write. Transaction shares the staff-administration advisory lock and rechecks actor, active target and unchanged grant/tenant mapping. Key `(entity_id,invoice_id)`; retain inactive history and audit actor/time. Owner reads are batched per bounded sales page; bills never query ownership. New forward-only migrations add connection read-health columns and backend-only assignment storage. Destructive statements: none. Hosted migrations remain unapplied.

Attachment decision: official invoice documentation allows 25 MB per attachment, whereas the generic attachment page still says 10 MB. Use a 25 MiB byte ceiling for invoice reads and document the discrepancy. Read metadata using the selected invoice, resolve attachment UUID to a verified filename, ignore provider URLs, and construct the fixed-origin path. Buffer at most one bounded file before sending success headers so truncated/provider-error bodies cannot become a successful partial preview. Timeouts remain bounded. Inline only signature-checked PDF/PNG/JPEG/GIF/WebP; all other content is a download. Official sources: https://developer.xero.com/documentation/api/accounting/attachments and https://developer.xero.com/documentation/api/accounting/invoices . No upload/edit/delete endpoints.
