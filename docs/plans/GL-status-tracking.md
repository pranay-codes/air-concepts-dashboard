# Green Line status tracking: investigation and implementation plan

**Goal:** implement the human-requested out-of-order tracking described in `docs/specs/GL-status-tracking.md` on a branch based on current `main`.

**Prompt contract:** Preserve tenant isolation, audit history and accurate sync status. A matching reference alone must not cause a cross-entity or ambiguous association. Do not report a provider result or sent state as confirmed without evidence. No real Xero writes, hosted database changes, deployment, or local PostgreSQL.

## Planned changes and tests

1. Research provider capabilities in official Xero and vWork documentation, as requested by the human, covering quote pagination, invoice matching and send state, and job identity. Update the applicable existing spike notes with findings and limitations. Do not remove existing fail-closed gates without evidence.
2. Add requirement-named tests in `StageMachineTest`, `InvoiceSyncTest`, `InvoiceMirrorServiceTest`, and their repository integration tests for an invoice sent before scheduling, uniqueness and entity isolation, repeated observations, and paid/voided invoices. Then adjust `StageMachine`, `InvoiceSync`, `InvoiceMirrorService`, and `InvoiceMirrorRepository` to satisfy those tests.
3. Add tests in `VworkSyncTest`, `VworkMirrorServiceTest`, and repository integration tests for a safely matched scheduled job observed before the expected quote transition and for changes after invoice linkage. Adjust `VworkSync`, `VworkMirrorService`, and `VworkMirrorRepository` while retaining provider and entity verification gates.
4. Add quote-refresh tests proving the documented and demonstrated end-of-results rule, duplicate and incomplete pages, and safe failure. Change `DocumentedQuoteSource` and `QuoteSync` only if provider evidence establishes the rule.
5. If display or API changes are required, follow `docs/ui-ux-design-specification.md` and the `api-contract` skill; test any affected dashboard state and generated contract. Do not introduce a database migration without its required review.
6. Run focused backend tests, appropriate frontend checks if changed, and CI-only database verification. Obtain the required independent review and open a PR against main with evidence and outstanding provider limitations.

## Definition of done

The reported sequence is verified end to end against synthetic tests grounded in provider documentation; safe out-of-order scheduling works with verified job identity; negative and cross-entity cases pass; failed/incomplete sync is not represented as success; the PR documents CI, independent review, and any outstanding account-specific and Test acceptance evidence. Real account testing is not represented as performed.

## Execution notes

- Baseline: `mvnw.cmd -q -B "-Dtest=StageMachineTest,InvoiceSyncTest,InvoiceMirrorServiceTest,VworkSyncTest,QuoteSyncTest" test` passed before changes.
- The Xero connector returned unauthorized when listing connections. Provider evidence remains outstanding; do not infer Demo access or provider behaviour from this result.
- Ruling, superseded after the human requested documentation-based testing: use Xero's documented reference search and sent indicator for early invoice discovery, with a matching contact, a single locally unambiguous reference and a single invoice result required before linking. Search results are re-read and the entity mapping, source data and reference collisions are rechecked under the write lock. The reference remains editable, so this is a conservative business-key association, not proof of an immutable provider link. Unverified vWork discovery stays gated.
- Ruling: an identifier match must have identifier boundaries, so a reference containing `Q-10` does not count as a match for `Q-1`. This prevents a partial identifier from linking the wrong invoice, but actual Xero reference formatting remains unverified.
- Independent Claude Code review (read-only, 23 November): the first pass could lose the work stage for an unsent or voided invoice, raise false quote-regression warnings after out-of-order transitions, and miss ownership handoff. Regression tests and corrections are in progress. The existing model does not record the earlier work stage after a sent invoice advances to Invoiced; a later void cannot always restore that stage safely. Resolve this before completing the feature.
- Other review findings needing resolution include bounded, fair candidate processing; isolation of ambiguous item failures; defence in depth for provider verification; tests for payment and void transitions; and the outstanding provider and UI evidence. The pre-existing live lookup's substring behaviour is unchanged and must not be mistaken for the stricter synthetic early-lookup check.
- The human confirmed there is no vWork Test account and instructed implementation from official vWork documentation. Account-specific identity, search and status semantics therefore remain unverified; the project security rules still require a trustworthy entity association before automatically linking a live shared-account job.
- The human requested Xero documentation-based testing. On 23 November, official sources confirmed that `SentToContact` reflects Xero's displayed sent state, and that invoice creation normally copies the quote reference or, if blank, its quote number. See `docs/spikes/gl-xero-invoice-write.md`. These facts do not establish an immutable quote-to-invoice ID, unique customer-provided references, or actual account response completeness.
- Ruling: use the documented Xero `SentToContact` signal for a linked authorised invoice. This means the invoice is marked sent in Xero, not proof of successful delivery to the customer. An absent signal remains unknown.
- Recovery implementation: for an early sent invoice subsequently voided, infer the work stage from the last linked-job observation or the prior audited stage, falling back to To invoice when neither is known. A paid item can reopen in the synthetic tracking path when a positive Xero balance is observed. These changes require CI-only database verification and further independent review. Real-provider paid-history polling remains gated to avoid an unbounded scan.
- The documentation-based Xero lookup requires the same Xero contact, one locally unambiguous identifier and one non-void invoice. Its bounded candidate batch rotates with the existing Xero sync-run ledger, rather than the clock, to avoid repeatedly selecting the same page on a regular schedule. Item-specific errors are collected without preventing other invoice checks; a partial invoice failure does not prevent the quote refresh, and the run remains failed. Incomplete quote pagination is still surfaced as a failed refresh. Live vWork auto-association and real paid-history polling remain gated. Account-specific behaviour is not verified.
- A clean focused run of the backend suite passed 107 tests, including documented copied references, duplicate identifiers, contact mismatches, absent sent indicators, early invoice and job transitions, void recovery and payment reversal. The newly added SQL integration cases compile but have not run locally; CI is required.

PostgreSQL tests were compiled but not run; no hosted provider verification was performed.
- Ruling: preserve explicitly selected vWork mock support in the `hosted` profile, as used by the existing deployment template. Both Test and Live use that profile, so it does not itself establish an environment boundary; Live-provider reference matching remains disabled.

Do not enable it until Xero daily-budget handling, database checks and the unresolved review findings are completed. The normal linked-invoice read uses the documented sent indicator without enabling early lookup.

Early sent invoices hand off to the finance owner, and invoice mirror writes and audit records include owner changes. SQL coverage is CI-only.
