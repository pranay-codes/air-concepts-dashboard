## Deviations from the approved plan
1. **Digests are pinned in the repo.** The Temurin digest is in `backend/Dockerfile`, and the Caddy digest is in the workflow's `env`. The plan had them as repository variables. Both are public digests, and keeping them in the repo makes them reviewable.
2. **Frontend settings come from SSM**, not GitHub variables. The workflow reads `/air-concepts/test/frontend/` with the deploy role. This needs `ssm:GetParametersByPath` on that path.
3. **Build is guarded to `main`.** `workflow_dispatch` can start a run on any branch, so the build job has `if: github.ref == 'refs/heads/main'`.
4. **Rollback is partly decided.** Automatic revert on a failed health check is implemented. Manual rollback is not: re-running an old run rebuilds and re-pushes its SHA tag, which fails with immutable tags and overwrites the tag otherwise. **Open decision:** add a manual input that deploys an existing digest without rebuilding?
5. **CORS needs a value for Test.** `backend/cors/allowed-origins` is optional in SSM, and the backend falls back to `http://localhost:5173`. The script warns if it is missing. Set it to the Test CloudFront origin before the first Test run. No code change is needed.
6. **Test fixtures use LF.** On Windows, text mode writes CRLF. The script rejects carriage returns, so the tests write LF explicitly. Set `TEST_BASH` to Git Bash on Windows so WSL's `bash.exe` is not used.

## Decisions to confirm in this plan
These are the spec's proposed defaults. The spec was approved as drafted, but the individual questions were not answered.

1. **Build runner:** `ubuntu-24.04-arm`, native arm64, no QEMU (spike: `ci-002-arm64-runner.md`). The minutes cost is recorded in the PR.
2. **Image contents:** the job builds the jar with `./mvnw -q -B -DskipTests package` and the Dockerfile copies it into a Temurin 25 JRE image. Packaging is done once, in the job, and Docker only packages it.
3. **Migrations:** unchanged. `supabase-migrations.yml` keeps running on `main`. No ordering is enforced by this workflow.
4. **Approval gate:** automatic on merge to `main`, with a manual run button for re-deploys.
5. **Rollback on failed health (changes AC-5):** AC-5 says the previous container keeps running. `docker compose up` replaces the container, so that is not possible as written. Proposed behaviour: when the new container is not healthy within the timeout, the remote script restores the previous digest, waits for healthy again, and then fails the job. The service stays up and the job still fails. This needs approval because it changes how AC-5 is met.
6. **Frontend API base URL:** a build variable `VITE_API_BASE_URL` set to the Test API origin. Confirm that the frontend reads this variable (not yet checked in `frontend/`).
7. **CORS:** `backend/src/main/java/com/airconcepts/dashboard/config/CorsProperties.java` exists. Confirm it reads allowed origins from configuration. If the Test CloudFront origin can be set through the existing backend Parameter Store path, no backend code change is needed. If it is hardcoded, this plan must be revised and the backend change gets its own review.
8. **Payload size:** the Compose and Caddy files and the script travel in the SSM command. Check the Run Command parameter size limit in the AWS docs before the first run. If it is too small, the files go to the Test bucket under a deploy prefix instead.
9. **Health wait on the host:** `docker compose up -d --wait --wait-timeout 180`. The `api` service is on an internal network, so the host cannot call `:8080` directly. The health check runs inside the container, and the public smoke check runs from the runner.
